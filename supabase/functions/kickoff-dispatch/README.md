# Kick-off update delivery

Candidate implementation, not provisioned or live. Design reviewed 14 October:
https://www.figma.com/design/NY8QhcuOWiEcD0pKDTsbP8?node-id=285-6351

Apply only `20261014105830_kickoff_updates.sql` after Mike names and approves that live database change under current ARCHITECTURE.md §2.10. Never use `db push` to apply unrelated pending migrations. New private tables hold versioned fixture events, account receipts, device subscriptions and an outbox. No historical backfill. Browser feature gracefully supports the previous database until this migration is applied.

Provision secrets in Supabase Edge Function Secrets Management, never in client code or a chat message:

- `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`: one matching P-256 VAPID pair, generated by pinned web-push 3.6.7; retain private key securely, do not rotate silently after subscriptions exist.
- `VAPID_SUBJECT`: approved club support mailto or HTTPS URL.
- `SMTP_HOST`, `SMTP_PORT` = **465**, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`: the club's approved transactional mail service and verified sender. Supabase Edge Functions block outbound SMTP ports 25 and 587; TLS port 465 is required for this transport. Auth SMTP and fixture mail are separate configurations.
- `KICKOFF_DISPATCH_TOKEN`: cryptographically random 32+ byte server secret for the scheduled invocation. Supabase supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to the function automatically.

Deploy `kickoff-dispatch` with `verify_jwt=false`; its constant-time bearer-secret check rejects all browser/user JWTs. No caller-supplied recipient, URL, payload or transport is used. Only service-role RPC grants allow outbox claiming. Keep the dispatcher token in Vault and invoke by a named pg_cron/pg_net job once per minute. Apply the separately named `20261014111626_kickoff_dispatch_schedule.sql` only after provisioning and named approval; do not put a literal secret in cron job text or a repository. Enable delivery flags via service-only `configure_kickoff_delivery(public_key,true,true)` only after both transports and the scheduled invocation pass a controlled test.

Validation without any real recipient: throwaway Postgres audience/grants/receipt/version/lease tests, synthetic Chromium UI, mocked dispatcher tests, actual Web Push encryption request construction and Deno module check. Actual device delivery, mail delivery, sender verification and schedule execution must be validated after provisioning before claiming LIVE. Use an explicitly authorised test account/device and dry-run/controlled send; never test by notifying the whole club.

Push requires an explicitly enabled browser subscription. Unsupported devices, blocked permission or absent transport configuration show unavailable. Push content is generic on the lock screen; a click opens the signed-in Notifications view and never acknowledges. Email includes only public fixture data. Seeing, reading and transport acceptance remain different states.

Retries are bounded to five attempts and use expiring claim tokens. Expired endpoints are removed. A retry after a worker crash between external acceptance and the database receipt can duplicate an SMTP message; stable Message-ID mitigates but cannot guarantee deduplication. `sent` means the push/mail service accepted the request, not proof that a human or device saw it. Devices use a 30-day renewable subscription lease, refreshed during normal notification use, and are unsubscribed on logout. Revocation and changed fixture details are checked immediately before send; external services cannot retract a message already accepted.
